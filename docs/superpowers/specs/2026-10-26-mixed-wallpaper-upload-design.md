# 同型号静态与动态壁纸统一目录方案

日期：2026-10-26。状态：已实现并验证。动态视频素材及网页预览仅支持 MP4；生产与本地数据库、已入库素材完成规范化，执行结果及回退材料见 `docs/wallpaper-admin-operations.md`。应用生产部署按 AGENTS.md 等待确认。

## 1. 目标与总体模型

同一品牌的同一设备或系统只有一条设备记录、一个默认上传目录。静态图片和动态视频可放在同一型号文件夹，一次选择、自动识别、分别入库。前后台按媒体类型管理合集内容。

- 设备身份：现有 `w_devices.id`，继续按品牌、归一化设备名查重，稳定 slug 用于公开路由。
- 合集身份：`device_id + media_type`，沿用已有逻辑，不新建合集表。
- 素材身份：现有 `w_wallpapers.id`，类型来自原文件内容，封面不是独立素材。
- 上传目录：设备级设置，与 `media_type` 解耦；数据库中的对象 key 是每个历史文件的实际读取位置。
- 型号名称、品牌归属、设备分类、发布日期共用；静态和动态的主图、多语言、素材发布与删除分别处理。

本次覆盖目录规则、混合上传、后台设备及合集操作、发布检查、权限校验和历史兼容。自动转码、自动生成封面、真实 Live Photo 图片/视频成对封装、历史文件批量搬迁另行立项。

## 2. 当前代码依据与需要解决的问题

- `src/lib/wallpaper-db.ts` 和 `migrations/0012_collection_media_scope.sql` 已支持同设备两种媒体类型，名称唯一约束为 `(device_id, media_type, name)`，主图唯一范围为 `(device_id, category, media_type)`。
- `src/app/api/admin/upload/route.ts` 完成上传时已依据原文件 MIME 判定类型；授权仍依赖调用方指定的媒体类型。
- `src/app/manager/AdminConsole.tsx` 的 `uploadMedia` 控制整批文件、目录、授权及新合集提示；文件按去掉扩展名后的名字归并，同名图片和视频会冲突。
- `src/lib/admin-upload-storage.ts` 阻止选用另一类型的目录，并要求新动态文件放在 `live/` 下。
- `src/lib/admin-data.ts` 的 `publish_drafts` 会处理设备下所有草稿；主图检查没有逐媒体、逐分类核对。`device-check` 同样只给设备级总计。
- 动态前台按 D1 的 `media_type` 查询；视频预览由原始 key 将 `/origin/` 替换为 `/preview/` 推导，播放和下载没有必须使用 `live/` 根目录的要求。
- 按类型删除已有引用保护、快照与重试机制；统一目录后仍应依赖记录及对象 key，不能按目录递归清空。
- 仓库已有 Node 测试，虽然 AGENTS.md 中“未配置自动化测试框架”描述较早，但本次无需新增测试框架。

## 3. 本地素材和 R2 目录规则

建议素材结构：

```text
Xiaomi 17/
  origin/
    mountain-static.jpg
    mountain-live.mp4
  compress/
    mountain-static.webp
    mountain-live.webp
  preview/
    mountain-live.mp4
```

- `origin` 必需：图片原图或原始视频。
- `compress` 必需：对应原图的网页压缩图，或视频的静态封面。
- `preview` 可选：动态视频的网页播放版本，文件名和扩展名必须与原视频一致。
- 每次选择一个设备/系统目录；沿用目前单型号上传边界。
- 文件直接位于三个角色目录，不支持再嵌套任意层级。`.DS_Store`、`._*`、来源说明文本等非素材文件忽略并列出数量；出现在角色目录中的其他疑似素材但不支持的格式报错，不静默遗漏。

新设备默认 R2 前缀沿用现有品牌与设备名称规则：手机等为 `<brand>/<device-name>`，桌面为 `desktopwalls/<brand>/<device-name>`。动态新上传同样使用此目录。品牌标识复用现有规范化结果，设备名称保持现有安全大小写与空格规则，不额外改变公开 slug。

### 3.1 目录持久化

仅依赖历史文件推断目录无法可靠表达“以后统一上传到哪里”。建议新增一个设备级字段：

| 字段 | 类型 | 默认值 / 可空性 | 业务含义与约束 |
| --- | --- | --- | --- |
| `w_devices.upload_prefix` | TEXT | `NULL`，可空 | 未来上传使用的 R2 相对前缀；不含尾斜杠和角色子目录，最长 300 字符；归一化后非空，禁止路径穿越、协议、控制字符和现有非法字符；非空值唯一 |

数据库用 CHECK 约束长度、非空及基础路径边界，用唯一部分索引保证非空值不重复；完整路径规范由现有 `normalizeAdminR2Prefix` 统一验证。R2 大小写敏感，不将历史对象 key 自动改成小写。

设置目录还要检查该前缀下已入库素材是否属于其他设备，包括待删除记录，不能仅凭唯一索引判断所有权。未入库的 R2 文件不能自动认领、覆盖或清理；同名对象存在时上传仍拒绝。

迁移只加字段和索引，历史值全部为 NULL，不自动搬文件。后台给出建议目录：

1. 已设置 `upload_prefix`：直接采用。
2. 未设置且存在唯一的非 `live/` 静态历史目录：优先建议该目录。
3. 只有历史动态目录或没有素材：建议新的统一目录，展示旧目录以供核对。
4. 存在多个静态历史目录或目录属于其他设备：要求明确选择，不随机选一个。

首次统一上传前保存该设备的上传目录；设备改名不改上传前缀、不搬文件、不改公开 slug。目录设置入口位于设备编辑页，上传页提供快捷入口，默认折叠历史路径。新设置使用统一命名空间；旧 `live/` 文件仅作为历史读取位置保留。

修改上传目录只影响后续授权。设备删除流程中禁止修改；已有队列须重新预检。授权绑定当时的目录；完成入库允许使用此前合法签发且仍有效的目录授权，不因目录随后调整而丢失已经上传的文件，但仍必须检查设备及当前类型的删除锁、文件归属和过期规则。

### 3.2 文件配对与重名

- 先扫描 `origin`，每一个有效原文件创建一条素材候选，再附加封面与视频预览。
- 用文件主名精确配对；文件名大小写敏感，必要时做近似提示但不自动改变大小写匹配。
- 原文件 `mountain-live.mp4` 对应 `compress/mountain-live.webp`，不是将封面再识别为一张静态壁纸。
- 同一主名有多个原文件（如 `01.jpg + 01.mp4` 或 `01.jpg + 01.png`）、多个封面（如 `01.jpg + 01.webp`）时判为歧义，阻止该项上传，要求改名或在界面显式选择配对；不以扫描顺序覆盖文件。
- 首版优先提供清晰改名提示；显式选择配对的交互可由实施者评估是否必要，不作为自动猜测的替代。
- 孤立封面、孤立视频预览单列“未匹配文件”，提供补充原文件或移除操作，不静默忽略。
- 原文件名与封面名保留；显示名称可以编辑，但不反向修改本地文件名、对象 key 或配对结果。
- `-static`、`-live` 是推荐命名，绝不是判型依据。

## 4. 类型识别与校验

| 原文件 | 归类 | 配套文件 |
| --- | --- | --- |
| JPEG / PNG / WebP / AVIF / GIF | `static` | 必须有图片压缩预览 |
| MP4 | `dynamic` | 必须有图片封面；MP4 播放预览可选 |
| WebM / MOV / HEIC / ZIP 等 | 新上传不支持 | 提示在上传前转换 |

本期 `dynamic` 明确定义为视频壁纸。动画 GIF、动画 WebP 仍按图片素材处理，界面提示此约定；不声称会提取所有图片格式的动画信息。

动态原视频和网页预览只接受 `.mp4` 与 `video/mp4`。现有代码仍包含 WebM 支持，实施时同步收紧后台文件选择、客户端校验、服务端上传授权与完成校验，避免只修改提示文案。历史素材按已保存类型和 key 继续读取；本项限制作用于新上传，不自动修改或删除已有 WebM 记录。

浏览器用 MIME 与扩展名给即时反馈；服务端不能把调用方声明或 R2 的 Content-Type 当成内容证明。完成入库前读取有界文件头，验证容器/图片签名、扩展名、MIME 与授权类型一致，再复用原始尺寸读取逻辑。MP4/AVIF 不能仅凭都含 `ftyp` 就混为同类，需要检查品牌/容器信息；不能证明是允许格式时失败而非猜测。

授权阶段：原文件请求类型由逐项识别结果生成；封面和预览授权绑定同一设备、同一条素材组、同一媒体类型和同一目录。完成阶段以实际原文件验证结果为准，不接受把视频手工改为静态，也不通过单纯修改后缀转换格式。

维持目前图片 50 MiB、视频 200 MiB 上限，沿用登录与同源写入验证、签名直传、条件写入、防覆盖和禁止路径穿越机制。Edge 上只做有界检查，不安装 FFmpeg 或长时间转码。

没有 `preview` 时允许按现有代理尝试播放原视频；后台明确显示“未提供网页预览，播放取决于原视频编码”。提供 MP4 容器不等于保证所有浏览器解码成功。

## 5. 后台调整

### 5.1 设备目录与设备详情

默认以设备为一行，展示品牌、名称、设备分类、发布日期、静态数量、动态数量、设备可见状态和上传目录配置状态。展开后分别展示静态、动态合集，沿用类型筛选。

这样型号基本信息只编辑一次。每种合集独立提供“查看素材 / 上传补充 / 主图 / 多语言 / 发布检查 / 发布或下架 / 删除合集”。空设备仍可编辑、上传和删除；上传第一条素材自然形成该类型合集，不再把“创建静态合集/动态合集”作为上传的前置操作。

新增设备仍需明确品牌、归一化名称、设备分类、发布日期。选择型号文件夹后按当前品牌匹配型号，不根据文件夹内容创建第二个同名设备；未找到时先确认创建设备，再继续原队列。

合集状态由素材状态派生，显示“草稿 / 已发布 / 部分发布 / 待重试删除”等。设备状态是上层可见开关：设备下架时两个合集均对外隐藏，必须在操作文案中写明影响。发布单个合集时如设备未发布，提示将同时打开设备可见开关，并列出另一个合集已有已发布素材是否也会恢复可见；不允许隐式恢复另一合集。

如要只恢复当前合集而保持另一合集隐藏，先将另一合集的已发布素材转为下架；这属于用户明确选择的另一项操作，不能在本次发布中自动修改。初期沿用设备状态加素材状态，不为此新增合集发布状态表。

### 5.2 上传工作区

交互顺序为：选择品牌及型号 → 选择型号文件夹/补充文件 → 自动识别和配对 → 检查队列 → 上传 → 选择发布范围。

- 删除整批必选的“静态/动态”控制；类型成为每条素材的只读识别结果。
- 上传页只显示一个当前设备上传目录，并能查看三个角色的落点；配置操作放在“目录设置”中。
- 单文件模式保留三个角色入口：“添加原文件”（允许图片和视频）、“添加预览图/封面”、“添加网页预览视频”。
- 队列顶部显示“静态 N 张、动态 M 个、待补文件 K 项、冲突 L 项”，可筛选类型和问题。
- 每条显示缩略图、媒体类型、原文件/封面/网页预览、大小、已知尺寸、主题、标签、目标目录和状态；动态显示播放预览是否提供。
- 缺文件、重复主名、类型不符、同名对象存在等错误定位到具体文件；默认阻止有问题的队列上传，用户可移除问题项后继续。
- 保留目标锁定；队列已有授权或上传中时切换设备、目录必须清空授权并重新预检，禁止把旧授权复用到新目标。
- 上传完成先形成草稿；已发布设备补充新文件同样不自动发布。

### 5.3 上传结果与发布

结果分静态和动态显示成功、失败、保留草稿数量。提供“重试失败项”“查看成功素材”“保留草稿”“发布选中素材”。部分失败不抹去成功项，也不触发“整批全部成功”的误导提示。

默认发布候选只包含本次成功入库的素材 ID。操作者可以选择静态、动态或两者；若要发布该合集以前的草稿，必须通过独立明确选择加入，不能使用隐式的设备全部草稿操作。

发布检查按每个实际影响的 `(device_id, category, media_type)` 进行：

- 原文件及预览/封面存在、大小和已核验信息一致。
- 删除锁未占用，记录版本与确认时一致。
- 该范围在发布后具有有效已发布主图；另一种类型的主图不能代替。
- 已有已发布主图可继续使用；若主图仍是未选中的旧草稿，提示选择本次素材作为主图或明确加入旧主图，不能偷偷发布旧草稿。
- 如需切换主图，把所选范围内主图调整与发布在同一 D1 事务中处理，遵循已有唯一索引。
- 多语言缺失显示提醒，沿用现有英文/默认语言回退，不将“五语言全部完整”设为这次新增的强制门槛。

页面所有“发布设备及其全部草稿”入口都要明确区分设备可见开关与素材发布，上传完成弹窗不再调用原有无范围 `publish_drafts: true`。

### 5.4 素材、多语言与删除

- 素材列表默认可查看同型号全部素材，保留静态/动态筛选、独立数量和格式标记。
- 素材编辑中媒体类型只读；换原文件导致类型变化时走新上传，不直接重分类一条已发布记录。
- 多语言窗口在标题显示“型号 · 静态/动态”，分别使用现有两套翻译表；可提供显式“复制名称”便捷操作，不自动覆盖介绍和 SEO。
- 按类型下架只修改当前类型已发布素材为 `unpublished`，保留原草稿为草稿，另一类型不动；下架前展示数量和快照。
- 删除合集沿用已有精确文件清单、引用保护、快照校验、删除锁和重试；删除动态时保留静态数据及其五语言，反之亦然。
- 共用封面按实际引用保留；不能执行整个 R2 型号目录递归删除。默认新上传不主动共用封面。
- 删除最后一个合集继续沿用现有设备保留/清理规则；同名文件重新上传仍受已删 key 保护，应改用新文件名，不悄悄解除墓碑。

## 6. 数据与接口设计边界

保留 `media_type`、`origin_key`、`compress_key`、现有名称和主图唯一范围、两套翻译表、稳定公开 URL。除 `upload_prefix` 外，本期不新增素材字段、不新增持久上传批次表；视频预览 key 继续按既有规则推导。

| 范围 | 调整 |
| --- | --- |
| 设备 GET/PATCH | 读写设备级 `upload_prefix`；改目录只影响后续上传，服务端校验所有权及并发版本 |
| 上传 GET | 返回设备统一上传前缀、配置状态、历史目录及两种合集概要；旧 `media_type` 参数可接收但不用于分配新目录 |
| 上传 authorize | 每项携带识别后的媒体类型；签名绑定素材组、设备、角色、目录；不再要求动态 key 以 `live/` 开头 |
| 上传 complete | 校验同一素材组的授权与实际文件头；返回素材 ID、最终类型、状态和是否为主图；禁止覆盖不相关记录 |
| device-check | 支持类型及选中素材 ID 的发布预检，返回分类型/分类计数、主图问题及待发布清单快照 |
| 新增受限发布操作 | 建议 `POST /api/admin/collections/publish`，显式提交设备、素材 ID、版本快照和必要的主图选择；返回精确成功范围 |
| 新增合集下架操作 | 建议 `POST /api/admin/collections/unpublish`，按设备、类型和清单快照操作，不影响另一类型 |
| 删除、多语言接口 | 保留现有类型范围，检查界面入口和文案与设备合并行一致 |

客户端在当前页面保留成功项 ID 与授权，重试时不重传已成功文件。不承诺刷新浏览器后恢复 File 对象或队列；刷新后通过后台素材列表查看已入库记录。

`complete` 必须支持同一授权组重放时返回同一素材结果。为避免新增全局原图唯一约束破坏历史共用素材，服务端可按签名组确定稳定新记录 ID，以 D1 主键约束处理并发，并核对所有已绑定字段；相同 key 被其他记录占用或请求字段不一致时返回冲突，不能认领别人的素材。具体摘要实现由实施者选择。

未入库但已上传的文件不自动删掉；本次结果展示已上传 key 和失败阶段，支持当前页重试完成入库。过期后由管理员核对孤立文件清单，确认数据库无引用、无有效上传授权后再清理；本期不新增自动清理任务。

## 7. 前台与公开接口

静态品牌页与动态壁纸页继续按 `media_type` 查询，不从 `live/` 前缀判断类型。前台数量、搜索索引、SEO、sitemap 和小程序接口核对其类型范围及发布条件，避免同一设备混放后数量翻倍或封面串用。

原图下载继续走 `/api/files/download`，视频预览继续走带发布检查与 Range 支持的 `/api/files/preview`。新统一目录与历史 `live/` key 均通过精确 D1 引用授权；不新增公开 R2 扫描入口，不暴露原始签名 URL。

如现有公开列表缓存不能随发布/下架立即失效，沿用并明确现有缓存时效，实施时验证不会把目录或类型作为错误缓存键。型号公开 URL、slug 和语言切换不因目录合并改变。

## 8. 历史兼容、上线与回退

第一阶段完成配置字段、混合上传、逐项授权、类型/配对校验、受限发布和必要的后台操作调整；第二阶段将设备列表切换为一设备一行并整合详情入口，两阶段功能全部完成才视为本方案交付。可用预览部署验证，不直接替换线上数据。

上线顺序：

1. 导出 D1 备份和历史目录审计清单，验证新增可空字段与唯一索引迁移。
2. 发布兼容新字段的后端及后台；生产部署、远程迁移遵循用户确认规则。
3. 选一个已有静态/动态型号和一个新型号，分别验证完整工作流。
4. 开放混合上传，历史 key、设备 ID、slug、发布日期和原发布状态保留。

正常读取历史素材不依赖 `upload_prefix`。新字段可空，旧代码可继续读旧记录；但旧上传代码对新动态目录有不同策略，不能直接将代码回退视为上传也兼容。需要回退时先暂停新上传，保留新增字段与已经写入的记录，用补丁保留统一目录解析与精确发布，不能删除新增素材或盲目移除列。

要让全部历史素材物理集中到统一目录，另做“复制 → 校验字节数与哈希 → 更新 D1 key → 验证代理及引用 → 保留回退副本 → 清理旧对象”的迁移；本期不自动执行。

## 9. 验收与文档同步

必须覆盖以下结果：

1. 同一目录的图片和 MP4 一次入队，分别进入正确类型；封面不多计为静态素材。动态原视频与网页预览的新上传均拒绝 WebM 等非 MP4 文件，改后缀也不能绕过校验。
2. 纯静态、纯动态、混合、只有封面、缺封面、同主名多原文件、多封面、大小写差异和不支持文件都有确定反馈。
3. 客户端伪造 MIME、扩展名不符、错误角色授权、跨设备/素材组 token、文件超限、路径穿越和同名对象不能入库。
4. 部分失败重试、complete 响应丢失重试、并发重复提交均不重复入库、不覆盖已有文件。
5. 同型号两种主图独立；发布本次静态不会发布动态或以前草稿；设备恢复可见时明确提示另一类型影响。
6. 删除/下架一种类型保留另一类型素材、翻译与被引用封面；删除锁、清单变化和失败重试继续有效。
7. 新目录及历史 `live/` 素材都能展示、播放、Range 请求及代理下载；未发布素材拒绝访问。
8. 改设备名、改上传目录、补充上传、未配置与多历史目录不会改变旧链接或把素材上传到错误目标。
9. 设备列表展开、类型筛选、移动端队列、错误定位与键盘操作可用，所有新增公共文案覆盖 en/zh/ja/vi/zh-hant。

实施时扩展现有 Node 测试覆盖实际风险，不新增测试框架；运行相关上传、发布、删除、预览、下载和公开数据测试，并按 AGENTS.md 执行 `npm run lint` 与 `npm run build`。开发服务器由用户启动，不删除运行中的 `.next-dev/`。

实际实施字段迁移时，同步 `docs/wallpaper-admin-d1-design.md` 的字段、默认值、约束与业务含义；同步 `docs/wallpaper-admin-operations.md`、相关 API 和历史动态导入文档及受影响 README。实际代码改动更新待发布版本 Release Note，版本取远端最新正式 tag 的下一补丁号。本设计文档本身不新增发布条目。

## 10. 建议优先级与交付范围

P0 是目录与类型解耦、无歧义配对、逐项授权/入库、限定发布范围、分类型主图和删除保护，必须一起交付，不能只放宽上传校验。

P1 是后台设备合并行、合集状态、详情入口与类型统计，与 P0 一并纳入本次完整方案，可分提交实施。

本期完整结果是：管理员选择一次型号文件夹，看到明确识别结果，将同型号两类素材上传至统一目录，再独立发布、补充、翻译、下架或删除对应合集；历史资源继续可用。
